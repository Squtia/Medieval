# 專案架構與遊戲平衡評估

> 評估日期：2026-08-12  
> 評估範圍：目前工作目錄中的實作、測試、平衡資料與既有模擬工具  
> 注意：評估時工作目錄包含尚未提交的變更，因此本文描述的是當下版本，而非特定 Git commit。

## 1. 執行摘要

專案已經具備完整的遊戲骨架，不再只是概念原型。核心狀態、遊戲日循環、系統層、資料層、UI controller、地圖、存檔及測試均已有明確分工；經營、探索、戰鬥、擴張之間也已形成可遊玩的循環。

目前最主要的風險不是個別技能多出 10% 傷害，而是設計資料、測試規格、模擬工具及實際程式已出現漂移。這會使後續平衡調整缺乏可信的比較基準。

| 評估項目 | 分數 | 摘要 |
| --- | ---: | --- |
| 整體架構 | 6.5 / 10 | 分層方向正確，但全域狀態、事件生命週期及大型類別提高維護風險。 |
| 遊戲循環合理度 | 6 / 10 | 經營與戰鬥循環已成立，但雙重威脅及軟鎖狀態需要處理。 |
| 平衡可信度 | 4 / 10 | 難度規格不一致，戰鬥屬性單位混用，既有平衡模擬已不符合現行資料結構。 |

## 2. 驗證結果

評估時執行的檢查結果如下：

- TypeScript 型別檢查通過。
- Production build 成功。
- Bundle budget 通過，產物為 `2,245,843 / 2,300,000` bytes。
- 14 個測試檔中 12 個通過、2 個失敗。
- 39 個單元測試中 36 個通過、3 個失敗。
- Smoke test 未通過；主要失敗原因是測試期待普通難度的玩家基地為 `NodeLevel.TOWN`，實際產生的是 `NodeLevel.WILDERNESS`。
- 5v5 平衡腳本可執行，但使用舊裝備欄位，結果不適合作為正式平衡依據。

失敗的單元測試：

1. 存檔 schema 已更新至 4，但測試仍期待 schema 3 資料完全不變。
2. 測試要求簡單難度的生產倍率高於普通，實際四種難度皆為 1。
3. 測試期待困難難度從村莊開始，實際設定為荒野。

## 3. 架構評估

### 3.1 優點

- `core`、`models`、`systems`、`data`、`ui` 與 `templates` 已有可辨識的責任分層。
- `GameLoop.advanceDay()` 提供統一的每日推進入口，主要流程容易追蹤。
- `EventBus` 降低部分系統與 UI 的直接相依。
- 世界生成支援 seed，可重現特定地圖。
- 存檔具有 schema migration，並針對舊資料補預設值。
- 地圖、探索、道路、戰鬥、存檔及平衡資料已有一定程度的自動測試。
- Phaser 地圖與 DOM UI 採分工設計，方向合理。

### 3.2 高優先級架構風險

#### A. EventBus 生命週期不完整

`initGameState()` 與 `SaveManager.loadGame()` 都會呼叫 `EventBus.clearAll()`，避免系統重複訂閱。這個方向合理，但清除時也會移除 UI controller 的訂閱。

重新開局或讀檔後只會呼叫 `rebindGlobalUIEvents()`；探索與酒館 controller 的 `DAY_PASSED` 訂閱只在應用程式首次啟動時建立。可能造成：

- 探索 UI 不再每日自動刷新。
- 酒館旅客雖然更新，畫面快取卻不再清除。
- 未來任何 controller 級事件都可能在重新開局或讀檔後失效。

建議：

- 將系統事件與 UI 事件拆成不同 bus 或不同 subscription scope；或
- 所有 controller 提供可重複呼叫的 `bindEvents()`／`unbindEvents()`；或
- `clearAll()` 改成只清除指定 scope，不清除整個應用程式的監聽者。

#### B. 全域 GameState 形成 service locator

多數 systems、UI controllers 與部分資料邏輯直接讀寫 `GameState`。短期開發快速，但長期會造成：

- 單元測試必須共同修改全域狀態。
- 系統執行順序成為隱性規格。
- 存檔載入、重新開局及模擬測試容易互相污染。
- 很難獨立模擬經濟、戰鬥或地圖系統。

建議逐步讓核心 systems 透過 constructor 或 method parameters 接收所需狀態；不必一次全面重構。

#### C. 部分檔案責任過多

目前較大的核心檔案包括：

- `ForgeUIController.ts`：約 1,265 行。
- `SkillData.ts`：約 1,225 行。
- `MapScene.ts`：約 911 行。
- `UIManager.ts`：約 716 行。
- `CombatSystem.ts`：約 658 行。
- `DispatchModalController.ts`：約 657 行。

建議優先依穩定邊界拆分，而不是只按行數拆分：

- Combat：隊伍建構、回合排程、AI 決策、傷害結算、戰報統計。
- SkillData：按基礎職業或技能類型分檔。
- UIManager：純畫面更新、overlay 管理、格式化／presentation helper。
- Forge UI：配方、強化、素材、渲染與 DOM binding。

#### D. 動態 import 未形成有效切包

建置時多個模組同時被靜態及動態 import，因此動態 import 無法真正移出主 chunk。Phaser chunk 約 1.7 MB，主程式約 426 KB。

目前 bundle budget 仍通過，但距離上限只剩約 54 KB。後續新增內容前，應先確定真正需要 lazy-load 的模組只從動態入口引用。

## 4. 遊戲循環合理度

### 4.1 已成立的核心循環

每日流程大致為：

1. 推進日期並重置每日狀態。
2. 更新天氣、市場及酒館旅客。
3. 推進派遣、探索與道路工程。
4. 模擬地圖動態及節點解鎖。
5. 觸發隨機事件。
6. 發送 `DAY_PASSED`，結算領地生產、人口及威脅。
7. 每七天支付維護費及傭兵薪資。
8. 推進懸賞與隨機侵略。
9. 每月模擬世界地圖及附庸發展。

這個順序大致合理，也使「內政準備 → 派遣／探索 → 戰鬥 → 戰利品與擴張 → 更高維護成本」形成閉環。

### 4.2 初期糧食模型

普通難度起始人口為 10，另有 1 名冒險者，每日基礎消耗約 11 糧。

- 每名農夫基礎產出 3 糧。
- 高治安提供 1.2 倍生產。
- 配置 4 名農夫時，每日約生產 14 糧，形成約 +3 的小幅盈餘。

因此玩家只要理解並及時分配人力，普通難度的初期生存壓力基本合理。需要注意的是，所有人口起初都是未分配狀態；若教學或 UI 提示不足，玩家會把可避免的飢荒誤認為系統不公平。

### 4.3 雙重威脅排程

目前存在兩套獨立壓力來源：

- `ThreatSystem`：約每 15～25 天觸發天災或威脅。
- `GameLoop.handleRandomInvasion()`：另以約 15～25 天的獨立 cooldown 觸發侵略。

兩者都受難度的 `threatInterval` 影響，因此高難度下不只事件更頻繁，也可能在相近日期甚至同一天疊加。玩家難以從 UI 預測總風險。

建議建立統一的「世界壓力排程器」：

- 每個時間窗口有固定威脅預算。
- 重大事件之間保留最短安全間隔。
- 已預告的威脅應降低其他突發重大事件機率。
- 難度提高威脅預算，而非單純壓縮所有計時器。

### 4.4 財務軟鎖

金幣允許降至負值，欠薪會觸發局部懲罰，但不一定形成明確失敗或復原機制。玩家可能進入長期負債、無法投資、又不會正式 Game Over 的狀態。

建議增加至少一種復原路徑：

- 緊急低收益工作或皇家貸款。
- 可解雇、遣散或降薪的明確介面。
- 負債達門檻時觸發重整事件。
- 將破產列為清楚的失敗條件。

## 5. 難度平衡

### 5.1 設定與介面不一致

資料中存在簡單、普通、困難、極難四種難度，但 `DIFFICULTY_ORDER` 目前只列出普通與困難，因此簡單與極難無法從正常新遊戲介面選擇。

### 5.2 生產倍率未形成難度差異

四個難度的 `production` 皆為 1，領地生產也沒有使用此倍率；但極難說明仍寫著「生產與探索收益最低」。目前實際難度主要來自：

- 初始資源差距。
- 敵人倍率。
- 探索收益倍率。
- 維護費倍率。
- 難民機率。
- 威脅間隔。

建議先決定難度哲學：

- 若難度只影響起步與外部壓力，移除 `production` 欄位並修正文案與測試。
- 若難度應持續影響整場戰役，則應讓生產倍率真正進入公式，並避免和維護費形成過度雙重懲罰。

### 5.3 起始據點規格漂移

目前設定：

- 簡單：首都。
- 普通：荒野。
- 困難：荒野。
- 極難：荒野。

但單元測試期待困難為村莊，Smoke test 又期待普通為城鎮。三者無法同時成立。

這會直接影響設施等級上限：荒野只能建到 Lv.1、營地 Lv.2、村莊 Lv.3、城鎮 Lv.5、首都 Lv.7。起始據點不是單純畫面差異，而是整段科技與建築進程的核心設定，必須優先定案。

## 6. 戰鬥平衡

### 6.1 閃避值單位不一致

動態怪物生成時，閃避值使用近似比例的 `0～0.5`；戰鬥命中公式則將閃避當作面板點數，與命中相減後除以 100。

結果：

- 動態怪物的閃避幾乎沒有作用。
- 手工建立或舊資料中的敵人可能使用 15、30 等完全不同尺度。
- 同一難度下，不同遭遇來源可能有巨大命中率差異。

建議統一使用「點數制」或「百分比制」，並在型別及欄位名稱中表明單位，例如 `evadeRating` 或 `evadeChance`。

### 6.2 爆擊率沒有封頂

技能爆擊率為 `0.05 + hit / 500`，進階武器再增加 10%～25%，但最終沒有 clamp。高命中角色可達到甚至超過 100% 爆擊率。

建議：

- 封頂在 75%～90%；或
- 使用遞減收益公式；或
- 將命中與爆擊拆成獨立屬性，避免命中同時提升可靠度與爆發。

### 6.3 閃避同時決定先手

回合排序以 `stats.evade + random` 決定，註解卻寫「依敏捷排序」。這使閃避同時提供：

- 更高躲避率。
- 更早行動。
- 更容易在對方行動前擊殺或控場。

建議新增獨立 `speed`，或直接使用敏捷／固定 initiative 公式。

### 6.4 MP 回復上限不一致

角色實際最大 MP 通常由 `SPR × 5` 決定，但每回合 MP 回復的部分邏輯使用固定 200 作為上限。低精神角色可能回復到超過面板最大值，高於 200 的角色又無法正常依真正上限回復。

建議將 `maxMp` 存入 `CombatParticipant`，所有消耗、回復與 UI 都只使用該欄位。

### 6.5 既有 5v5 模擬不可作為基準

本次執行結果：

| 陣容 | 勝率 |
| --- | ---: |
| 極致物理單體 | 1% |
| 極致魔法群攻 | 0% |
| 混沌特效連鎖 | 0% |

但腳本把武器與防具加成寫入舊的 `stats` 欄位，現行 `Adventurer.getCombatStats()` 只讀 `effects` 與 `combatEffects`。腳本宣稱的 +150 攻擊、+500 HP、+100 防禦實際未套用，因此以上勝率不能代表正式遊戲平衡。

建議重建測試 fixture，直接使用正式裝備模板或與 `Equipment` 型別相符的資料。

## 7. 建議的平衡驗證框架

### 7.1 固定角色基準

至少建立以下測試隊伍：

- Lv.1：初始裝備、單人與三人隊伍。
- Lv.5：一般品質裝備、標準三職隊伍。
- Lv.10 未轉職：中高階裝備。
- Lv.10 已轉職：Tank／Healer／3 DPS 標準隊伍。
- 特化隊伍：純物理、純魔法、混沌、控制、持久戰。

### 7.2 固定敵人基準

- 同級普通怪：目標勝率 75%～90%。
- 同級精英：目標勝率 50%～70%。
- Boss：在正確配置下目標勝率 35%～60%。
- 越級敵人：應明顯危險，但保留少量策略取勝空間。

### 7.3 應記錄的指標

- 勝率及 95% 信賴區間。
- 平均回合數與超時率。
- 各職業傷害、治療、承傷與控制貢獻。
- 首回合死亡率。
- MP 耗盡回合。
- 每場損失的兵力、恢復時間及預期淨收益。
- 不同元素、地形與陣型對結果的影響。

平衡不能只比較戰鬥勝率，也要把戰利品、傷亡、休養時間及派遣機會成本納入。

### 7.4 長期經濟模擬

建立 30、180、360 天的 seeded 模擬，至少覆蓋：

- 各難度的糧食破產率。
- 人口平均值及變異。
- 金幣淨流量與負債率。
- 首次建築升級所需天數。
- 首次形成完整隊伍的時間。
- 威脅失敗率及事件疊加次數。
- 村莊、城鎮、首都的平均到達時間。

## 8. 建議處理順序

### P0：建立可信基準

1. 決定普通與困難難度的正式起始據點。
2. 同步 `DifficultyData`、單元測試、Smoke test 及文件。
3. 更新存檔 migration 測試至 schema 4。
4. 修復 5v5 腳本的裝備 fixture。
5. 確保完整 `npm run check` 通過。

### P1：修正會影響實際遊玩的結構問題

1. 修正 EventBus 在重新開局及讀檔後遺失 UI 訂閱的問題。
2. 統一閃避單位。
3. 為爆擊率加上限。
4. 將 initiative 與 evade 分離。
5. 統一最大 MP 與回復公式。
6. 整合 Threat 與 Invasion 排程。

### P2：重新校準經濟與難度

1. 決定 `production` 是否應受難度影響。
2. 執行長期經濟模擬。
3. 檢查負債軟鎖與恢復路徑。
4. 校準起始資源、維護費、探索收益與威脅頻率。

### P3：內容與職業微調

1. 在可信模擬環境下比較各職業。
2. 調整技能倍率、冷卻與 MP 成本。
3. 校準怪物 HP、攻擊、防禦及掉落。
4. 最後處理元素、兵種與陣型的細部倍率。

## 9. 結論

核心玩法方向合理，系統內容也已足以支撐一款經營型傭兵 RPG。現階段最值得投入的工作，是讓規格、測試和實作重新對齊，並修復事件生命週期與戰鬥單位問題。

在驗證基準恢復可信之前，不建議大規模微調技能或敵人倍率；否則很可能只是在補償測試工具、起始規格或屬性單位造成的誤差。

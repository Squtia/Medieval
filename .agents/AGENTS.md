# AI 助理行為準則 (Agent Guidelines)

## 1. 語言規範 (Language)
- **繁體中文溝通**：所有回覆、說明、代碼注釋與討論，一律使用繁體中文（台灣語系）。

## 2. 測試與異常中斷機制 (Testing Loop Limit)
- **嚴格執行兩次限制**：當代碼測試或除錯迴圈（Debug Loop）超過 2 次（即第 3 次失敗）時，必須立刻終止自動測試。
- **中斷後的行動**：終止後，必須暫停並提供以下選擇給使用者：
  - 👉 提出當前困境與其他可行的替代方案。
  - 👉 提示使用者：「已達測試上限，請考慮更換 AI 模型進行測試」。

## 3. 編碼前置確認 (Pre-coding Alignment)
- **禁止直接撰寫代碼**：在開始任何實際編碼（Coding）工作前，必須先與使用者進行確認。
- **不要馬上寫報告，先討論**：在產生正式的實作計畫（Implementation Plan）或任何形式的報告文件前，必須先以對話的形式與使用者逐一討論想法與設計細節。
- **執行一個編碼後，收到問題回報**：收到問題回報後，不要馬上編碼。
- **優化流程討論**：動手前，需先將思維轉入「討論模式」，主動與使用者分析、討論架構與優化過程，得到明確授權後方可開始寫代碼。

## 4. 文件同步更新與交接機制 (Documentation Maintenance)
- **強制記載開發日誌**：每次完成更新或修改後，必須同步更新 `docs/CHANGELOG.md` (開發日誌)。
- **維護專案架構與交接**：若有架構變動，必須更新 `docs/ARCHITECTURE.md`；且在階段性任務完成或暫停時，更新 `docs/HANDOVER.md` (交接文件)，以利使用者閱讀與未來交接作業。

## 6. HTML 檔案保護規則 (HTML File Protection Rules)

### index.html 守則（架構拆分後適用）
- **禁止**對 `index.html` 使用 `Overwrite: true` 整塊替換
- `index.html` 僅為 ~38 行的骨架，任何 UI 元素都應修改對應的 template 檔案
- 修改前必須先用 `view_file` 確認 `index.html` 目前內容，確認它仍是骨架

### Template 檔案對應表
| 要修改的 UI 區塊 | 對應檔案 |
|---|---|
| 全域 CSS 樣式 | `style.css` |
| top-bar, overlay, tooltip | `src/templates/ui-chrome.html` |
| 主選單、地圖、野外、街道視圖 | `src/templates/views-main.html` |
| 書房、謁見廳、酒館、商店、鍛造屋 | `src/templates/views-facility.html` |
| 右側共用面板 | `src/templates/views-right-panel.html` |
| 戰鬥 Modal、貿易 Modal | `src/templates/modals-combat-trade.html` |
| 倉庫/新遊戲/載入/派遣/俘虜/系統/事件/待辦 | `src/templates/modals-game.html` |
| 左側抽屜面板、HUD、每日結算 | `src/templates/panels-hud.html` |

### Git 操作守則
- **禁止**在未確認 commit hash 與 diff 的情況下執行 `git reset` 或 `git checkout` 來恢復 HTML 檔案
- 每次修改 template 前，建議先 `git add` 備份當前狀態

### 精確編輯守則
- 修改任何 template 或 `style.css` 時，必須先用 `view_file` 確認 `StartLine` / `EndLine`
- 優先使用 `multi_replace_file_content` 精確替換，避免大範圍整塊替換
- 每個 template 檔案 < 400 行；若超過此限制，應考慮繼續拆分

## 7. 嚴禁應試思維與偽完成原則 (Anti-Cheating & True Implementation Mandate)

### 7.1 嚴禁「以指標與測試全綠冒充功能完成」（杜絕指標綁架）
- **全域強制適用**：本原則適用於專案所有模組（包含但不限於戰鬥、內政、大地圖、經濟、敘事、工坊、UI 與資料庫系統），任何情境與功能皆不得違背。
- **測試通過 ≠ 功能完成**：自動化測試全綠、TypeScript 0 錯誤、無頭腳本 0 報錯，僅為程式碼無語法崩潰的最低門檻，**絕對不得以此作為「功能已正常可用」的交付藉口**。
- **嚴禁撰寫「應試欺瞞代碼」**：
  - 嚴禁為了讓測試斷言（Assert）通過，只修改內部狀態或模擬變數，卻未真正貫通底層邏輯、狀態機、視覺渲染或實質資料管線。
  - 嚴禁 UI 控制項只將資料寫入記憶體 Store，真實業務邏輯、底層演算法與畫面卻毫無實質動態反饋。
  - 嚴禁以 Mock 自身邏輯、寫死返回值、固定超時等待（Timeout）或吞掉異常來假裝系統已非同步完成。
  - 任何無法在真實使用者操作中產生實質預期效果的實作，一律視為重大工程違規。

### 7.2 嚴禁「架構惰性與表層敷衍（地基腐朽、塗脂抹粉）」
- **依真實使用情境建構架構，嚴禁不適當套用**：
  - 編輯器/工坊類系統必須具備編輯器級架構（如即時求值、確定性狀態/影格渲染、所見即所得、持久定格、熱更新）。嚴禁直接拿實戰一次性運行的拋棄式邏輯（播完即自毀）敷衍拼裝。
  - 業務與結算系統必須具備嚴密的資料閉環與不變量守護。嚴禁僅在前端顯示上修改數字，而未真正觸發後端計算與持久化。
  - 嚴禁為了「看起來能跑」而在舊的、不適用的架構外層套皮。若既有底層架構無法支撐功能需求，必須主動向使用者提出重構底層，絕不得在腐朽地基上層層包裹無效的抽象層欺瞞使用者。

### 7.3 強制「真實使用者視角審查（Human-Centric Audit）」
- 在交付任何功能、模組或系統修復前，必須站在「真實人類玩家/創作者親手操作」的立場進行全流程自我檢驗：
  1. **實質響應檢驗**：使用者操作介面上的任何按鈕、滑桿、欄位或控制項時，系統有產生實質、可見、可感知的動態響應嗎？（若操作後無實質效果即違規）
  2. **狀態與互動一致性檢驗**：當使用者進行暫停、拖曳、倒退、重整或切換時，畫面與內部狀態是否完全同步且真實可交互？（若狀態脫節、物件蒸發、各跑各的即違規）
  3. **資料閉環檢驗**：數值的變更是否真實作用於底層業務邏輯與持久化存檔，而非僅停留在前端局部變數？（若刷新後丟失或底層未吃數值即違規）
  4. **全路徑體驗檢驗**：使用者從入口進入、操作、到結果產出，是否能順暢走完全部流程？（若中間存在斷點、假按鈕、未綁定事件或硬編碼繞過即違規）
- **上述任一項檢驗未達標，嚴禁宣稱「完成」、「已修好」或「驗收通過」，必須誠實向使用者回報真實進度、客觀限制與待解決斷點**。

## 8. 禁止空口憑空推測與強制代碼查證防線 (Anti-Hallucination & Code Truth Mandate)

### 8.1 嚴禁未查證即斷言（杜絕憑感覺瞎猜）
- **禁止憑記憶或舊印象臆測系統運作**：在回答使用者關於「某功能是否存在」、「兩系統是否有衝突」、「底層邏輯如何運作」等問題時，**嚴禁直接依賴 LLM 自身推論回答**。
- **凡發言必有行號與代碼引用**：任何架構解釋、邏輯推論或問題診斷，**必須先調用 `codebase-memory` 查出呼叫鏈，或使用 `view_file` 閱讀真實檔案**。
- **回答中必須強制附帶證明**：
  1. 具體檔案路徑與精確行號（例如：`CombatFXEngine.ts:1020-1050`）。
  2. 真實執行的代碼片段。
  3. 若無法提出真實代碼呼叫鏈證明，一律禁止得出「這有衝突」或「這不相容」的結論。

### 8.2 優先調用 MCP 工具檢驗真相
- 遇到架構與相依性問題，強制先執行以下動作之一方可開口回答：
  - 調用 `call_mcp_tool(trace_path)` 追蹤真實呼叫端點。
  - 調用 `call_mcp_tool(search_code)` 或 `grep_search` 確認函式真實引用。
  - 調用 `view_file` 查閱實作細節。
- **違背此條款（未調用工具即妄加論斷）視為重大工程違規**。

## 9. 全專案通用架構契約規範 (Universal Data Flow Rule)
- **強制全域適用**：在修改專案中「任何」功能時，Agent 必須強制遵循以下原則：

### 9.1 識別資料管道的兩端 (Two-End Identification)
- **雙端同步定位**：任何改動只要涉及「使用者操作 $\to$ 系統反應」或「模組 A $\to$ 模組 B」，動手前必須同時定位：
  - 📤 **【輸入/發送端】**：UI 組件、輸入事件、指令發起處。
  - 📥 **【處理/接收端】**：狀態管理器 (State/Store)、底層運算邏輯、執行器。
- **嚴禁單端作業**：嚴禁只讀取或只修改其中一端，必須確保兩端資料流向貫通。

### 9.2 必須具備唯一真理來源 (SSOT Enforcement)
- **明確型別與結構定義**：兩端之間傳遞的資料物件，必須有明確的型別定義（Type/Interface）或資料架構（Schema）。
- **嚴禁手寫字串字典**：嚴禁在發送端和接收端各自使用手寫的字串字典（Raw Object / ad-hoc 鍵值對）。
- **先行建立共享型別**：若兩端尚未建立共享型別，必須先建立獨立的型別定義，讓兩端共同引用，方可開始修改功能邏輯。

### 9.3 跨端交付前核對 (Cross-End Verification Before Delivery)
- **欄位契約 100% 對齊**：每次修復宣稱完成時，必須確認發送端發出的欄位名稱與接收端讀取的欄位名稱 100% 相同。
- **資料閉環實質確認**：確認發送端動作能實質傳遞至接收端並被正確解析處理，嚴禁任何一端欄位脫節。


## 10. 型別防護規範 (Type Safety Mandate)
- **業務與資料傳遞嚴格禁止**：凡涉及特效參數、資料庫、事件廣播（EventBus）與 UI 對接的欄位，嚴禁使用 `any`、`as any` 或 `// @ts-ignore`，必須提供完整的型別定義。
- **禁止空泛轉型**：嚴禁使用全可選屬性（全是 `?`）或空介面來規避檢查。
- **引擎例外需說明**：僅在調用第三方圖形庫（如 Phaser/Canvas）且缺乏原生型別時允許局部轉型，且必須在回覆中註明原因。

## 11. 嚴禁表層抹平技術債與反妥協防線 (Anti-Compromise & Root-Cause Mandate)
- **嚴禁順著爛代碼滑坡**：當發現既有代碼存在 `as any`、`any` 或混合了已淘汰的舊型別（例如在 Sequence 架構中調用舊世代 Preset）時，**嚴禁為了求快或避免報錯而在表層套皮、打補丁或順著舊架構寫相容黑魔法**。
- **主動揭發底層債務**：遇到型別腐敗或架構斷層時，必須主動向使用者揭露問題本質，並提出「拔除 `any`、淘汰舊型別、對齊唯一真實來源 (SSOT)」的根治療法。
- **違者判定**：任何「一臉正經講幹話、用爛方法補洞、試圖掩蓋底層架構腐朽」的行為，一律視為重大工程違規。

## 12. 全專案通用架構倫理與正交不變量規範 (Universal Architectural Ethics & Invariants)
- **全系統通用強制適用**：本規範適用於專案中「所有」子系統（包含但不限於：戰鬥數值與職業技能、領地內政與經濟結算、UI 介面與資料驅動、3D 圖形渲染與著色器、音效與動畫管線），任何情境與功能皆不得違背。

### 12.1 關注點正交解耦與無損組合性原則 (Orthogonal Compositionality & Lossless Combination)
- **維度正交獨立**：
  在系統架構中，兩個在概念上獨立的維度（如「結構形態」與「材質質感」、「業務邏輯」與「表現渲染」、「角色職業」與「裝備外觀」），在程式碼實作中**必須維持 100% 正交（Orthogonal）**。
- **嚴禁「耦合綁架」**：
  嚴禁在維度 A 的處理邏輯中硬編碼寫死維度 B 的實作（例如：在某技能機制中寫死特定數值公式，或在某材質 Shader 函式中寫死特定幾何形狀）。
- **嚴禁「因切換維度而降級或丟失」**：
  嚴禁因為使用者變更了維度 A，系統就粗暴地將維度 B 丟棄、閹割或降級為劣質實作（例如：切換幾何外形就把 Shader 扒光變成單色塑膠材質；切換裝備外觀就把技能效果洗掉）。
- **無損組合承諾**：
  系統必須保證維度 A 與維度 B 的任意交叉組合（$A \times B$），都能以等同的完整品質無損協同運作。

### 12.2 真誠對待操作入口與拒絕「虛假開放」(Honesty in Exposure & Full-Pipeline Reactivity)
- **操作入口真實承諾**：
  **凡是暴露給使用者操作或外部調用的入口（UI 控制項、API 參數、設定檔欄位），系統必須對其承諾 100% 的實質動態反饋**。
- **嚴禁「擺設型控制項」與「快取死鎖」**：
  嚴禁「只在初始化或初次加載時讀取一次參數，後續變更因快取/內部狀態存在而完全不予更新」的欺瞞行為；嚴禁「UI 表面提供選項，底層卻各自寫死常量」的假開放。
- **全管線穿透反應 (Full Reactivity)**：
  任何輸入端數值的變動，底層接收端、狀態層與計算/渲染層必須具備即時熱響應能力，保證「所見即所得 (WYSIWYG)」與真實資料閉環。

### 12.3 杜絕割裂組裝與單一裝配真理來源 (Single Assembly Pipeline Mandate)
- **唯一流水線原則**：
  全系統中同一類業務實體、運算對象或渲染對象的裝配與生命週期，必須擁有**唯一確定性的裝配流水線（Single Assembly Pipeline）**。
- **嚴禁各自手寫多套拼裝**：
  嚴禁在「單體操作」、「群體/批次操作」、「編輯器/預覽端」、「實戰結算端」各自用 ad-hoc 的方式複製黏貼、私自微調拼裝邏輯。
- **統一語義與數學不變量**：
  所有方向向量、座標系定義、單位量綱、時間尺度與縮放倍率，必須在系統級別具備唯一真理來源，嚴禁不同模組各憑感覺補償正負號或旋轉角度，導致全局語義分裂與回歸 Bug。

## 13. 資深偷懶工程師原則與反過度設計天梯 (Ponytail & Minimal Implementation Mandate)
- **常駐自動生效**：本原則全域常態啟用，Agent 在每一輪編碼、重構與修復時，**必須自動遵循以下 7 層決策天梯與最簡設計守則，完全不需使用者手動提醒**。

### 13.1 核心決策天梯 (The 7-Rung Ladder)
在開始撰寫任何程式碼前，強制停在第一個能解決問題的階梯，絕不往下多走一步：
1. **階梯一：這功能真的需要存在嗎？ (YAGNI)**
   - 預期性、猜測性、未來可能用到的需求：直接略過，一句話向使用者說明。
2. **階梯二：專案現有程式碼裡有了嗎？ (Reuse it)**
   - 優先翻找現有的 helper, util, type, store 或 pattern。
   - 嚴禁「自己重新手寫一個幾行之外就有的東西」（這是最常見的垃圾代碼 Slop）。動手前先讀。
3. **階梯三：標準函式庫能做嗎？ (Stdlib)**
   - 語言原生標準庫（如 Object.assign, Array.prototype, URLSearchParams 等）能解的直接用。
4. **階梯四：原生平台功能有支援嗎？ (Native Features)**
   - HTML 原生 `<input type="date">` 優於龐大的 Datepicker 套件；
   - CSS 樣式/動畫優於複雜的 JS 輪詢；
   - 資料庫約束優於應用層硬防禦。
5. **階梯五：已安裝的相依套件能解嗎？ (Installed Dependencies)**
   - 複用既有依賴。絕不為幾行代碼就能寫好的功能引入全新的 npm 套件。
6. **階梯六：能一行解決嗎？ (One-liner)**
   - 能用一行純粹運算解決的，絕不開函式、開類別、開介面。
7. **階梯七：真的都不行時：才寫剛好能跑的最小可行程式碼 (Minimum Viable Code)**
   - 寫出通過需求與測試的最小 Diff，絕不擴大戰線。

### 13.2 先讀懂呼叫鏈，再爬天梯 (Read First, Then Climb)
- 天梯是本能反射，不是偷工減料的藉口。
- 天梯必須在**徹底閱讀受影響程式碼、查明呼叫端（Grep/Trace）**之後執行。
- 在錯誤的地方做最小改動不是偷懶，那是製造第二個 Bug。

### 13.3 根因修復大於表面補丁 (Root Cause over Symptom)
- 使用者回報的是「症狀」。動手修改前，先查閱所有調用該模組的端點。
- **最偷懶的修復就是根因修復**：在共享函式/底層核心加上一道防禦，勝過在每一個呼叫端各自打補丁。
- 嚴禁只修表面回報的路徑而留下其餘破碎的呼叫端。

### 13.4 嚴格禁令與架構守則 (Anti-Over-Engineering Guardrails)
1. **嚴禁未受請求的抽象層**：
   - 只有一個實作的 Interface ➔ 刪除，直接用 Class 或 Type。
   - 只有一種產品的 Factory ➔ 刪除，直接 new。
   - 永遠不會變更的設定檔 (Config) ➔ 刪除，直接寫常量。
2. **嚴禁提前搭鷹架**：
   - 絕不為了「未來可能擴充」而預寫空介面、抽象基類、適配層。
3. **刪除優於新增**：
   - 枯燥、樸素、可讀的代碼，勝過精巧炫技的高深代碼。
4. **最少檔案原則**：
   - 能在現有檔案順暢閉環的，絕不輕易拆出多個新檔案。最短的有效 Diff 就是最優雅的 Diff。
5. **偷懶但絕不偷工減料 (Lazy, Not Negligent)**：
   - **資安邊界、型別安全、資料丟失保護、錯誤處理與無障礙功能**，絕對不在精簡砍除的清單內！安全與穩定是偷懶的基石。

## 14. 上下文保護與 Token 節約規範 (Context Protection & Token Conservation Mandate)
- **常駐自動生效**：為防止對話上下文迅速膨脹導致 Token 浪費與記憶壓縮中斷，Agent 必須強制遵守以下執行約束：
  1. **嚴禁無差別全庫測試**：在開發除錯與模組驗證期間，**嚴禁執行全庫級別測試指令**（如未帶目標路徑的 `vitest run`）。
  2. **強制定向精準測試**：驗證時必須精確指定單一測試檔案或特定 test case（例如：`npx vitest run src/ui/fx/VFXDeterministicPlayback.test.ts`），將終端 stdout 輸出量控制在極小範圍內。
  3. **抑制大輸出與管道過濾**：若必須執行可能產生大量輸出的指令，必須主動配合 `--silent`、`--reporter=dot` 或適當管道過濾，避免上千行終端日誌淹沒對話上下文。
  4. **精準閱讀避免巨幅拉取**：禁止反覆大範圍切片檢視大檔案。查閱前必須先用 `grep_search` 定位具體行號，`view_file` 僅讀取核心邏輯之最小必要區間（原則上一次不超過 30 行）。
